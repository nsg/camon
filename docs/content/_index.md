## Storage Tiers

Video is stored across two tiers today, with a third planned. Hot and warm tiers store data as-is from the camera (H.264 passthrough) for performance — no transcoding overhead. Hot storage keeps ~10 minutes in RAM at full quality (1080p @ 30fps) for live playback, scrollback, and real-time analysis while minimizing disk writes. Warm storage keeps events on disk per class — movement events for 2 days, object events for 14 and continuous chunks for 1 by default, each configurable between 1 and 3650 days. A cold tier that transcodes to lower resolution (480p @ 5fps) for long-term archival (weeks–months) is planned.

Warm events are assembled from GOP-aligned segments (keyframe to keyframe) and written to disk the moment their motion run ends, with configurable pre-padding (default 5s) and post-padding (default 10s) to capture context around the event — an event is only at risk in RAM for seconds after it ends, not for the lifetime of the hot buffer. Typical GOP is 1-2 seconds (~750KB–1.5MB at 6 Mbps), though this depends on camera settings.

A single event is capped at `max_event_duration_secs` (default 120s). Sustained motion past the cap is flushed as a complete, independently playable chunk and continues in a new one, keeping RAM and file sizes bounded and preventing gaps when a run outlives the hot buffer. Follow-on chunks carry no pre-padding and a `"continues"` sidecar flag so the UI can stitch the chain. All event-lifecycle timing — the post-padding countdown and the duration cap — runs on a monotonic clock rather than media PTS, so a camera timestamp jump or reset can't stall or prematurely close an event; media timing (segment durations, playlist math, filenames) stays on PTS.

When a motion event ends, the system reaches back into the hot buffer for the preceding context (pre-padding before the first motion), capturing what led up to the event.

### Recording modes

What warm storage records depends on the `storage` and `analytics` flags together. With analytics enabled it is **event recording**: only motion and object events land on disk, in `movements/` and `objects/`. With analytics disabled the same combination becomes **continuous recording** — a "dumb NVR" mode. Without an analyzer to gate on motion, a per-camera recorder rolls every hot-buffer segment to disk in fixed-length chunks (each `max_event_duration_secs` long) under `continuous/`, flagging successive chunks `"continues"` so the timeline stitches together. Because chunks split on whole GOP segments, each `.ts` starts with PAT/PMT and a keyframe and plays on its own. Continuous recording is heavy — roughly 43 GB/day/camera at 4 Mbps — so `continuous_retention_days` defaults to 1, far shorter than event retention. Both modes share the same warm writer, retention pruning, and HLS playback; only the trigger differs. Disabling storage entirely leaves live view only — camon states which mode it is in at startup, and warns when analytics is left on without storage, because motion is then detected, published to Home Assistant, and discarded.

Whatever the mode, a camera can end up recording nothing while everything still looks healthy: an ignore mask painted over the whole frame, a sensitivity slider at its least sensitive, a stream that never reaches camon, or warm writes that keep failing all produce the same empty event list. A per-camera silence watchdog warns when a camera has written no event for too long — ten missed chunks (20 minutes at the default cap) in continuous recording, where a chunk is due on a fixed cadence, and 24 hours in event recording, where an empty scene is a legitimate reason to be quiet all night. The silence is measured from the newest event on disk rather than from process start, so a restart does not forgive it, and each warning reports the whole silence. Cameras that are not expected to record are not watched.

Access is abstracted behind a unified interface — consumers request video by time offset, and the system transparently serves from the appropriate tier.

## Camera Pipeline

Cameras stream H.264 via RTSP. The system uses FFmpeg to ingest RTSP streams, outputting MPEG-TS format to stdout. An MPEG-TS parser extracts H.264 frames and detects keyframes via the random_access_indicator in the adaptation field. Segments use wall-clock timestamps for timing.

## Camera Requirements

Cameras must provide an RTSP stream with H.264 codec at 1080p 30fps. Keyframe interval should be 1-2 seconds (GOP 30-60 frames) with bitrate around 6 Mbps. CBR or capped VBR recommended.

## Concurrency

Each camera has its own hot buffer using a single-producer, multi-consumer (SPMC) pattern. The ingestion thread writes while analytics and API read concurrently. Synchronization via `Arc<RwLock<HotBuffer>>` with minimal contention since there's only one writer per buffer.

## Analytics Pipeline

Cameras stream H.264 via RTSP into the hot buffer. Keyframes are sampled for analysis — with a 1-second GOP that is one frame per second. A segment says how many frames it owes: the decode ends once that many have arrived rather than when a timeout expires, so decoding is paced by the footage instead of by a fixed wait per segment. Frames that a decoder still owes for an earlier segment are discarded rather than scored against whichever segment is in flight. A segment whose frames never arrived produces no verdict at all — it is not recorded as quiet, because calling unseen footage motionless both hides it and splits an event across it. Motion detection (a built-in pure-Rust MOG2 background subtractor with a ~5 minute background memory, followed by morphological opening and connected-component filtering) produces scores and regions. Detection is deterministic and controlled per camera by three settings you edit live in the web UI: a sensitivity slider (MOG2 var_threshold), a minimum-object-size slider, and a paintable movement mask (a 16×12 grid — mask trees or busy roads so motion there is excluded). There is no automatic tuning. A second painted layer on the same grid, the detection mask, is independent of motion detection: its cells are blacked out of every frame sent to the vision model, so a stationary nuisance object (say a parked car) can be hidden from classification without suppressing motion there. When motion is detected, object detection via Ollama vision LLM identifies objects from a configurable class list (default: person, car, truck, dog, cat). While detection is on the list may not be empty, nor hold a blank entry: object detection has its own on/off flag, so an empty list is ambiguous between "detect nothing" and "detect the defaults" — omitting the key asks for the defaults, and camon refuses to start rather than guess which was meant. The classes it is given are the classes every consumer sees: the same list reaches the model and the Home Assistant bridge, read off the detector itself. Up to four cropped frames from the motion event are queued as a job for a single global detection worker shared by all cameras. They come one from each of four segments spread across the run, which is also where each frame's crop was measured, and four is all that is ever kept: the colour decode is thinned *as the frames arrive* rather than collected and reduced afterwards, so the live cost is a function of the four frames kept and not of the run's length or of `sample_fps`, which has no configured ceiling — at the model's input resolution one raw frame is 6 MB, a run's full decode was hundreds of megabytes live at once, and on a box whose memory is already contended that peak is the difference between recording and being killed. The handful of segments ahead of the run still go through the decoder, because ffmpeg emits nothing until it has probed that much input, but they are footage from before the motion and are dropped rather than shown to the model or kept as thumbnails. What ffmpeg swallowed while probing surfaces late, so the pipe is also drained before the run's own segments are read; unlike the analysis decoder above, the crop decoder keeps no arrears ledger and cannot usefully keep one, since its expected frame count is `sample_fps` times a duration — an estimate of what ffmpeg will emit rather than a parsed keyframe count — and a debt tracked against it would drift into discarding real frames. The drain therefore takes what has arrived and does not wait for what has not, which narrows the window in which a frame is credited to the wrong segment without closing it; keeping a spare frame per segment is what makes the remainder survivable, costing a lagging decoder a frame of the strip instead of all of it. The worker is strictly serial — at most one in-flight Ollama request at any time — so a modest GPU never sees parallel load, and motion detection never waits for the model (a full queue drops the job; the motion event still records). Requests use Ollama's structured output with a JSON schema — the class list as an enum, numeric confidence and normalized bounding box — and responses are validated before use; garbage is dropped. Every valid detection is recorded — nothing is silently suppressed. Events are written to disk the moment their motion run ends; a verdict that arrives later upgrades the on-disk event post-hoc from a movement to an object event (sidecar rewritten, files moved, retention class switched). An optional fallback Ollama server can be configured for redundancy.

## API

HTTP REST API for playback and search. Supports live and historical video playback by time offset, and event search by time range and camera. Setting `[http] token` puts every `/api` route behind a shared secret, sent as an `Authorization: Bearer` header — or, for GET and HEAD requests such as image and video URLs that cannot set headers, as a `?token=` query parameter. A request without it is answered `401` with `WWW-Authenticate: Bearer`; the UI shell and its assets stay outside the token layer so the prompt that asks for it can load. The token is optional: leaving it unset keeps the API open, and camon warns at startup when that is combined with a non-loopback `[http] bind`.

An event query takes wall-clock nanosecond bounds, either of which may be omitted, and matches by overlap rather than by start, so an event that began before the window and runs into it — a long continuous chunk, typically — is returned. A range whose `from` is greater than its `to` is a `400` rather than a guess. Writing motion settings answers `500` when the change could not be persisted; the change is applied to the running detector regardless, and the response says so, so a mask never fails silently. Semantic query and clip export are planned.

## Web Interface

Vanilla HTML/CSS/JS served from the Rust binary with video playback via Vidstack (CDN). No build tools required — cargo builds everything. Provides live view with scrollback, timeline scrubbing across tiers (transparent to user), and event search.

The event browser names each event by the type the API gives it — object, movement, or continuous-recording chunk — and gives each of those types its own filter, so none of them is reachable only under "All"; a type from a newer server than the UI is labelled by its wire name and left to "All" rather than filed under a filter it does not belong to. Chunks of one long recording — a motion run split at the duration cap, or the chunks continuous recording rolls — are railed together down the list. Membership is not taken from the `continues` flag alone, which outlives the chunk it points at: a chunk joins the one before it only if it also starts where that one ended. A chunk whose predecessor is still stored is numbered ("part 3"); one whose predecessor has been pruned is only marked "continued", since counting from the oldest surviving chunk would name a position the chunk does not have and would change with every retention sweep.

A settings change that did not stick is shown rather than swallowed: the motion-settings panel carries a dismissible error banner above it that repeats the server's own wording, and it distinguishes camon answering that a change was applied but not saved from camon not being reachable at all — one outcome is certain, the other unknown. The painted mask and slider positions stay as edited either way, because the running detector is using them.

## Home Assistant

Beyond running as an ingress add-on, camon can bridge to Home Assistant over MQTT (`[mqtt]` in the config; auto-configured from the Supervisor in the add-on). It publishes retained MQTT discovery messages so each camera materializes as a native HA device with four entity kinds: a snapshot camera fed with JPEG frames only while motion is active (decoded on demand from the newest hot-buffer segment — idle cameras cost nothing), a motion binary sensor tracking the physical motion run, one occupancy binary sensor per object-detection class that holds for a configurable time after the last sighting, and one snapshot camera per such class showing the cropped frame from the last sighting of that class (retained, so it persists across restarts). The bridge is strictly outbound — it subscribes to nothing — and marks all entities unavailable via a broker last-will if camon dies.

Since every state is retained, a bridge that dropped mid-motion would leave a motion sensor stuck on until that camera happened to move again. Each connect therefore restates every configured entity explicitly — the ones that are off just as much as the ones that are on — and publishes availability last, so nothing is marked available while the broker still holds a stale value. A publish the broker cannot be handed schedules the same restatement rather than being logged and forgotten. The same retention makes an entity the config *drops* — a renamed or removed camera, a class taken off the list — outlive it, availability flipping it back to life on every start; camon remembers the entity set it announced in `{data_dir}/mqtt_entities.json`, along with the broker it announced to, and clears the discovery document and state of everything the current set no longer explains at the head of the burst, before availability. That comparison is deliberately narrow, since clearing an entity costs its history and its dashboard placement: cameras come from the config as they are, but classes are carried forward whenever a run has none — carried forward and still announced, so object detection being disabled or its vision server unreachable leaves the occupancy entities in place, restated for what they are. A record written for a different broker is not authority to delete anything, and clears stay recorded as owed until a clean disconnect proves they left the process, so an unclean stop costs a redundant round of clears rather than a permanent ghost. Snapshots are the exception to queueing: while the link is down they are dropped rather than parked, because a several-hundred-kilobyte image is long superseded by the time it could be delivered, and each snapshot decode runs as a child process that gives up after 15 seconds and dies with its task, so shutdown can never be held up by one. Camera ids and object-detection class names both reach topics verbatim, so neither may contain an MQTT wildcard (`+`, `#`) while the bridge is enabled, and camera ids must stay distinct once slugified; camon refuses to start otherwise.

## Error Handling

Camera disconnections are handled with automatic reconnection using exponential backoff (5s, doubling up to a 60s cap, with jitter); the delay resets after a stream stays healthy. A data watchdog reconnects a stream that stops delivering bytes, and a tripwire reconnects one that delivers data but produces no keyframes. The analysis decoders get the same treatment: handing a segment to a decoder is bounded rather than blocking, so an FFmpeg process that stops reading its input is killed and respawned instead of freezing motion analysis, and a decoder that consumes segments without emitting frames is caught by a zero-frame tripwire and respawned too. A decoder that will not start at all — including at analyzer startup, where the failure used to end the camera's analysis for the life of the process — is retried on the same backoff (5s doubling to 60s, jittered so cameras that fail together do not retry in lockstep), with the error reported on a widening schedule rather than once a minute forever. Cameras operate independently — one disconnecting doesn't affect others. None of these waits outlive a shutdown request: a camera parked in its reconnect backoff and an analyzer waiting to respawn its decoder both wake immediately, so stopping camon never takes a minute of waiting for work that has already been abandoned.

A reconnect loop on its own says nothing about *why* nothing is being recorded, so each connection also reports what camon actually saw on it: whether any bytes arrived, whether they were a transport stream (and how much had to be resynchronized past), whether a program map named an H.264 elementary stream, whether packets reached that stream, and whether any of them flagged a random access point — the flag camon starts a segment on, and which some cameras never set, producing a stream that looks alive and yields no footage at all. Each report states what was observed and over how long, and offers the causes that fit rather than naming one; a connection too short to judge says so instead of accusing the camera. Repeated failures escalate on a widening schedule rather than repeating every minute, and the streak clears only when a connection actually records something.

An analyzer that falls behind loses segments to the hot buffer's eviction; those are reported as skipped footage — count and sequence range, at most one line per 30 seconds — rather than passing unnoticed.

## Self-update

Camon can replace its own binary from GitHub Releases (`[update] enabled`, off by default, since the installed service runs as root and releases are not signed). It checks at startup and every 12 hours; an update installed while it is running asks for the same graceful shutdown a SIGTERM does, and the service manager starts the new binary.

Because that restart is what completes an update, the updater is built so a bad release cannot turn it into a loop. A download must be a valid ELF and must match the release's `sha256sums.txt`; a release that publishes no checksums is refused rather than installed unverified, which is a change of stance made possible by every release since that file was introduced having one. What passes is then written beside the binary it would replace and run as `camon version` — bounded in how long it may take, how much output is kept, and by its own process group, which is killed afterwards so nothing it forked outlives it. It has to report exactly the version its release is tagged with. The tag is a label a human typed; the binary's own answer is what the *next* process compares against that tag, so an asset that is not the version it is published as would leave the tag still looking newer once installed, and camon would fetch it again after every restart. Refusing it before the swap is what makes that loop impossible rather than merely short. A binary that cannot answer is refused as well: it cannot be checked, and it may not run on this machine either. Refusals are recorded, so a broken release is not re-downloaded every twelve hours to reach the same verdict.

Versions are compared as semantic versions rather than as dotted numbers — a release outranks its own pre-releases, build metadata is not a difference, and anything camon cannot compare exactly it refuses instead of guessing — so a pre-release can be shipped and installed like any other version.

One failure remains that no check of the artifact can see: an install that works and never comes back, because the service starts a different binary than the updater replaces. For that, camon records each install in a `camon.update-guard` file beside the binary and installs the same version at most three times, then says so and stops. Any newer release resets the count and a record for one version says nothing about another, so the guard can only ever hold back a version that has already proven it does not take; deleting the file retries. One updater at a time touches an installation, held off by a lock file beside the binary, so two camon processes cannot each spend the same attempt. The swap the whole check leads up to is made durable like every other file camon has to find again after an unclean stop: the download is fsynced, and made executable, before it is renamed over the running binary, and the directory holding the name is fsynced afterwards. Renaming over a binary that is executing is an ordinary inode swap — the running process keeps the inode it started from until it exits — but the rename is atomic, not durable, and without those fsyncs a power cut moments after an update could leave a truncated or empty `camon` under the live name, which is an installation that no longer starts at all.

## System Dependencies

Camon builds into a single self-contained binary with a plain stable Rust toolchain — no OpenCV, no C++ toolchain, no native vision libraries. The motion detector (MOG2, morphology, connected components) and all image handling (cropping, JPEG encoding via the pure-Rust `image` crate) are Rust. Runtime requires FFmpeg for RTSP ingestion, H.264 handling, and motion analysis frame decoding. On Ubuntu/Debian:

**Build:** stable Rust only

**Runtime:** `ffmpeg`

Object detection requires a running [Ollama](https://ollama.com/) server with a vision model.

## Data Storage

Metadata is stored in memory. Video files are stored on disk.

Warm video files are stored per camera as `{data_dir}/{camera_id}/{movements|objects|continuous}/{timestamp}_{duration_ms}.ts`, where `data_dir` defaults to `/var/camon/storage`. The `continuous/` subdirectory holds chunks written in continuous-recording mode; `movements/` and `objects/` hold motion and object events. Cold archives are organized by date as `cold/{year}/{month}/{event_id}_{timestamp}.mp4` (planned).

Writes are durable: each event is staged as a `.tmp` file, fsynced, renamed into place, and the directory holding it fsynced after, so a crash or power cut never yields a torn or half-indexed event — and never loses a committed one either. The final step is the one that makes the commit stick: a rename is atomic but not durable on its own, and until the directory entry naming the file is on the disk a power cut can take the name away while the bytes survive, leaving footage camon has already reported as written unreachable. One directory fsync covers the whole event, since the sidecar and filmstrip thumbnails were renamed into the same directory just before the video. Their contents are deliberately not fsynced — the single contents fsync per event is spent on the video, which is what cannot be reconstructed, whereas a sidecar lost to a power cut costs only what it alone carries — the detected classes, their confidences, and the flag marking a follow-on chunk. What it does not carry is the event's type, which lives in the directory name: a scan reads an object event back as an object event, on its full retention, even with the sidecar destroyed. That is also why one directory fsync is enough. A movement→object upgrade moves the `.ts` between two directories and fsyncs both — the destination first, and no further if that fails, since making the removal of the old name durable while the new name is not is the one combination that loses the event outright; a source that cannot be synced is survivable by comparison, costing at worst the same footage listed twice, once as the object event and once as the movement it was. A commit whose directory fsync fails is reported as a failed write even though the event is on disk, indexed and playable: nothing is re-written or dropped by saying so (only an out-of-space outcome is ever retried), while calling it written would reset the camera's recording-silence watchdog and let a storage stack that is guaranteeing nothing look healthy. At the next startup any interrupted `.ts.tmp` is recovered rather than deleted — trimmed to the last intact MPEG-TS packet, its duration recomputed from the stream's PES timestamps, and indexed with a `"recovered": true` sidecar flag, with the directory fsynced so that the salvage survives a second cut — because an interrupted write may hold the footage of the very incident that cut the power. A `min_free_bytes` guard (default 2 GiB) emergency-prunes the oldest recordings — continuous first, then movements, then objects — whenever the storage filesystem runs low, so recording continues instead of failing on a full disk. Which filesystem that is gets checked rather than assumed: camon writes a `.camon-volume` marker into `data_dir` at startup and re-stats it once a minute, because an unmounted data directory is the one storage fault that looks like health from every other angle — the mountpoint is still a directory, so writes land on whatever is behind it (usually the root filesystem) and report success, the recording-silence watchdog is reset by exactly those successful writes, and `statvfs` answers for the wrong device. The single `stat` carries both facts that matter: the marker being absent says the tree camon initialised is not the tree it is writing into, which is what catches a bind mount going away without any change of device id, and the marker sitting on a different device says the volume was swapped or something was mounted over the path. Both are compared only against this process's own startup reading, which is never persisted — so a first run creating the directory, a relative `data_dir`, a bind mount, and an operator moving storage between runs are all silent, and no attempt is made to decide whether the path "is a mount point", the usual test for which (device differing from the parent's) calls every bind mount unmounted. The report is an error, repeated hourly, with a matching one when the volume returns; it is never fatal, since refusing to record turns footage in the wrong place into no footage at all, but the emergency prune stops for the duration, because deleting footage to free space on a filesystem the footage is not on is the only irreversible thing camon could do about it. In the same spirit, a stored-event directory that exists but cannot be read is warned about at scan time instead of skipped, which had made an unreadable archive indistinguishable from a fresh install.

Retention belongs to a single task for the whole store rather than to each camera's writer — a sweep covers every camera, so exactly one of them runs however many writers there are, instead of N whole-store sweeps racing each other — and it stops between events when camon is shutting down, never part-way through deleting one. An event leaves the index only once its video is actually gone: a delete that fails leaves it listed and playable for the next sweep to retry, rather than unindexing a recording that is still on disk with nothing left to describe it, and the emergency pass skips events it has already failed to delete so they cannot stand in front of events that would free space. The files of one event are unlinked in a fixed order — sidecar and thumbnails first, the `.ts` last — since unlinks are no more durable than a rename: the `.ts` is what the startup scan indexes and what retention measures, so leaving it as the survivor of an interrupted delete means the next sweep finds the event again and deletes the rest, where the opposite order strands metadata that nothing looks for and nothing collects, kilobytes at a time for as long as the installation lasts. A scheduled sweep deletes at most a quarter of a camera's events (at least four), so a clock corrected forward — routine on a box without a battery-backed clock, which resumes at its last shutdown time — cannot empty an archive in one pass; it warns loudly and the rest follows on later sweeps. The cap bounds scheduled retention only, since a disk that is genuinely full has to be freed. Retention days are validated at startup: whole days from 1 to 3650, with 0 rejected because it means "expired the moment it was written" rather than "keep forever".

The warm store sits behind a backend seam, so it need not be local. The default is local disk (above); adding a `[storage.stathost]` section instead sends warm events to a remote [stathost](https://github.com/nsg/stathost) static file host over HTTP, while analytics, motion settings, and the hot buffer stay local. On the host each event is three sibling objects under `{camera_id}/` — `{timestamp}_{duration_ms}.ts`, a `.json` sidecar, and eager `{stem}_thumb_{i}.jpg` filmstrip frames — with no directory tiers, so the sidecar carries the event **type** as well as its detections, and a movement→object upgrade simply rewrites that sidecar in place. Time-based retention still deletes expired events; retention-by-space becomes a client-side budget (`max_stored_bytes`), since the client can't see the server's disk. stathost commits uploads atomically, and camon uploads the sidecar before the video, so the video is the commit point: since the sidecar is the sole record of an event's type, an event whose sidecar cannot be stored is failed rather than written as a video that a later scan would mislabel as a plain movement and delete on the wrong retention. A sidecar that cannot be *read* back is treated the same way — unknown, not movement. Such an event is still indexed and served; only the decisions that need its type err toward keeping it, so age-based pruning measures it against the longest configured retention (nothing can expire later than that, and unlike an indefinite hold it does terminate) and budget eviction tiers it with the objects. Every prune tick re-reads those sidecars, which is the only retry there is — the scan itself runs once, at startup. Deleting and evicting borrow local disk's rules where the two fail alike. Within one event, thumbnails go first, then the video, then the sidecar: thumbnails carry nothing, while the sidecar is the sole record of the event's type, so keeping it until the video is actually gone means a refused delete is retried against the event's own retention — reading a type-less `.ts` back as a plain movement is not reliably a *shorter* life, since continuous retention defaults to 1 day against movement's 2 and the three are configurable in any order. Budget eviction demotes an event whose deletion the store refused to the back of its tier rather than trying it ahead of events that would free space, but never excludes it: a pass here stops at the first failure, and excluding as well would leave everything flagged during an outage permanently unreclaimable once the store returned, because the hourly sweep only retries events that are already age-expired. Space that was never reclaimed is not counted as reclaimed. Writing a stem that already exists is an update rather than a second event, since a `PUT` overwrites: the index replaces that entry and trims the filmstrip top-down to the frames the new version has, so a frame that refuses to delete leaves a still-contiguous strip the index can honestly claim instead of a permanent leak. The startup scan also deletes metadata whose video never landed — a sidecar or thumbnail of a failed upload is invisible to everything else here, because the index is built from `.ts` objects and siblings are only deleted with their event, so on a flaky uplink they would pile up untracked forever. It runs before any camera records, never queues a retry, touches only the cameras and object names this camon owns, and re-checks each candidate against the host immediately before deleting it, since a video can land after the listing was taken and only a confirmed absence is grounds to delete; the remaining window is one request round-trip, which no client can close without a conditional delete, and losing it costs a video its type record rather than any footage. Local disk deliberately has no such sweep — there, metadata is written before the video is committed, so "metadata with no video" is what an event awaiting crash recovery looks like. The scan has to complete before the first camera records — the index, the byte budget and that sweep's safety all depend on it — so it does not ask for one sidecar at a time: reads and orphan probes go out sixteen at a time, since a bucket holding a few thousand events is otherwise a few thousand sequential round trips of startup with nothing being recorded. That is a change to when requests are issued and nothing else: results are still consumed in listing order, so the index comes out as a serial scan built it, and each request still decides its own confirmed-absence-versus-could-not-tell. Each request to the host is bounded, since a warm writer awaits them inline: 10s to connect, 60s in total for a delete, a sidecar or thumbnail read, or the startup listing, and 300s for an upload, which must allow tens of megabytes over a slow uplink. Ranged playback deliberately has no total ceiling — it would cut off a player draining the body at its own pace — and is bounded by a 30s idle budget instead.
